# 제품 추천 기능 준비사항

## 1. 목표와 범위

제품 추천은 단순히 제품에 점수를 매기는 기능이 아니다. 사용자 상태, 제품 정보, 사용 맥락, 근거 수준을 함께 보고 **지금 사용해도 되는지**, **왜 그런지**, **확신이 부족하면 무엇을 더 확인해야 하는지**를 설명하는 기능으로 정의한다.

초기 범위는 다음처럼 좁게 시작한다.

- 대상 시술: 피코토닝
- 기간: 시술 후 D+0~14
- 대상 제품군: 현재 룰테이블이 지원하는 카테고리부터 시작
- 출력: `사용 가능`, `주의해서 사용`, `일시 중단`, `판단 정보 부족`
- 비목표: 피부 질환 진단, 이상반응 원인 확정, 치료 및 의약품 추천

## 2. 추천에 필요한 사용자 입력

### 2.1 반드시 받아야 하는 정보 (P0)

- 시술 종류와 시술일
- 현재 피부 상태
  - 붉음, 열감, 따가움, 가려움, 통증, 진물, 부종, 각질 등
  - 증상 강도와 시작 시점
- 평소 민감도
- 현재 사용하려는 제품과 카테고리
- 제품 전성분 또는 룰 판정에 필요한 제품 속성
- 시술 병원에서 별도로 받은 지침 유무

위험 증상이 있거나 병원 지침과 서비스 룰이 충돌하면 제품 추천보다 병원 문의 안내를 우선한다.

### 2.2 추천 정확도를 높이는 정보 (P1)

- 피부가 평소 건조한지, 유분이 많은지, 복합적인지
- 세안 후 당김 여부
- 향료, 에센셜오일, 알코올 등 사용자가 이미 알고 있는 기피 성분
- 알레르기 또는 의료진에게 피하라고 들은 성분
- 현재 함께 사용하는 전체 루틴과 사용 순서
- 제품별 사용 빈도, 사용량, 바르는 부위
- 최근 새로 추가하거나 사용량을 바꾼 제품
- 계절, 습도, 자외선 노출, 마스크 착용처럼 반응에 영향을 줄 수 있는 맥락
- 피부 질환 치료 중인지와 처방 제품 사용 여부

민감한 건강 정보는 꼭 필요한 경우에만 받고, 수집 목적과 저장 기간을 명확히 안내한다.

## 3. “안 맞는 성분”과 “안 맞았던 제품”을 받는 방법

사용자에게 안 맞는 성분만 묻는 방식은 부족하다. 대부분의 사용자는 정확한 원인 성분을 모르며, 제품 반응은 성분 하나뿐 아니라 농도, 제형, 동시 사용 제품, 사용량과 당시 피부 상태의 영향을 받는다.

따라서 두 가지를 분리해 수집한다.

### 사용자가 이미 알고 있는 정보

- 확정 알레르기 또는 의료진이 피하라고 안내한 성분
- 반복적으로 문제를 경험해 스스로 기피하는 성분
- 단순 취향으로 피하는 성분 또는 향

각 항목에는 `확정`, `반복 경험`, `추정`, `취향`처럼 근거 수준을 붙인다.

### 안 맞았던 제품 이력

- 정확한 제품명과 가능하면 당시 제품 버전/구매 시기
- 전성분 목록 또는 제품 페이지
- 나타난 증상
- 사용 후 증상이 시작된 시간
- 사용 빈도와 양, 사용 부위
- 함께 사용한 제품
- 당시 시술 여부와 피부 상태
- 사용 중단 후 호전되었는지
- 다시 사용했을 때 같은 반응이 반복되었는지

시스템은 이 이력으로 **의심 성분군 또는 의심 조합**을 만들 수 있지만 원인을 확정해서는 안 된다. 결과는 예를 들어 `향료 포함 제품 3개 중 2개에서 따가움 보고 — 관련 가능성 중간`처럼 관찰 근거와 신뢰도를 함께 보여준다.

## 4. 제품 데이터에 필요한 항목

### 제품 식별

- 브랜드, 제품명, 용량
- 바코드 또는 공식 제품 식별자
- 출시/리뉴얼 버전과 전성분 확인일
- 국내외 판매명 차이

### 성분 및 제형

- 공식 전성분(INCI 및 한국어 표기)
- 성분 동의어와 성분군 매핑
- 공개된 경우 농도, pH, 자외선 차단 지수
- 향료, 에센셜오일, 색소, 변성알코올, 계면활성제 등 룰에 필요한 속성
- 크림, 젤, 밤, 오일, 워터프루프 등 제형 및 사용 특성
- 세정력, 자극 가능성, 보습/밀폐 성향처럼 근거가 정의된 파생 속성

### 출처와 품질

- 공식 브랜드 페이지나 패키지 등 원문 출처
- 수집일과 마지막 검토일
- 자동 수집인지 사람 검수인지
- 불완전하거나 서로 충돌하는 데이터 표시
- 리뉴얼 감지 및 이전 버전과의 분리

## 5. 추천 엔진에 필요한 구성

추천 과정은 다음 순서로 구성한다.

1. 위험 증상과 진료 필요 여부를 먼저 판정한다.
2. 의료진 지침, 확정 알레르기, 명확한 금기 같은 강한 제외 규칙을 적용한다.
3. 시술 종류와 경과일에 맞는 제품 룰을 적용한다.
4. 현재 피부 상태와 과거 반응 이력으로 결과를 보수적으로 조정한다.
5. 함께 쓰는 제품과 사용 순서에서 생기는 중복/조합 위험을 확인한다.
6. 근거가 부족하면 억지로 추천하지 않고 `판단 정보 부족`을 반환한다.

각 판정에는 다음을 저장한다.

- 최종 결과와 핵심 이유
- 적용된 룰 ID와 룰팩 버전
- 사용한 사용자 입력과 제품 데이터 버전
- 근거 출처와 근거 수준
- 불확실성 또는 누락 정보
- 더 안전한 대안 행동

## 6. 사용자에게 보여줄 결과

- 결론을 한 문장으로 먼저 표시
- 결론을 만든 이유 2~3개
- 사용한다면 빈도, 양, 순서 등 구체적인 방법
- 중단해야 하는 증상
- 어떤 정보가 부족해서 판정이 보수적인지
- 제품 또는 룰의 마지막 검토일
- 잘못된 정보 신고 및 실제 사용 결과 피드백

`추천 점수 82점`처럼 근거가 불분명한 숫자보다, 조건과 이유를 설명하는 판정을 우선한다.

## 7. 실제 사용 후 피드백

추천 품질을 개선하려면 추천 당시 입력과 사용 후 결과를 연결해야 한다.

- 실제로 사용했는지
- 사용 횟수와 기간
- 문제가 없었는지
- 새 증상이 생겼다면 종류, 강도, 시작 시점
- 중단 후 호전 여부
- 다른 제품을 동시에 바꿨는지
- 추천이 이해하기 쉬웠는지와 도움이 되었는지

단일 사용 후기만으로 룰을 자동 변경하지 않는다. 반복 패턴을 후보 신호로 만들고, 근거 검토와 사람의 승인을 거쳐 룰팩을 갱신한다.

## 8. 상태 저장과 온보딩 지속성

### 현재 구현 확인

- `recovery-note:v1` 키로 동의, 시술, 제품, 체크인 정보를 브라우저 `localStorage`에 저장한다.
- 앱 시작 시 `StoreHydrator`가 저장 정보를 Zustand 스토어로 복원한다.
- 저장 데이터에는 `schemaVersion: 2`와 온보딩 진행 상태, 현재 단계, 완료 시각이 포함된다.
- 루트 페이지는 완료 사용자만 `/home`으로 보내고, 진행 중인 사용자는 마지막 단계로 복귀시킨다.
- 따라서 **같은 도메인과 같은 브라우저 프로필**에서는 새로고침, 탭 종료, 브라우저 재실행 뒤에도 저장 정보가 유지된다.
- 상태 필드가 없던 v1 데이터는 동의, 시술, 세안 답변을 기준으로 한 번 마이그레이션한다.

### 현재 한계

- 다른 기기, 다른 브라우저, 시크릿 모드에서는 이어지지 않는다.
- 브라우저 데이터 삭제 또는 저장소 정책에 따라 데이터가 사라질 수 있다.
- 재배포는 일반적으로 같은 도메인의 `localStorage`를 지우지 않지만, 도메인이 달라지면 별도 저장소로 취급된다.
- `productDraft`는 메모리에만 있어 제품 등록 도중 새로고침하면 사라진다.
- 동의 화면의 미제출 초안은 `sessionStorage`라서 같은 탭 새로고침에는 남지만 탭/브라우저 종료 후에는 보장되지 않는다.

### 필요한 개선 (P0)

- 제품 입력 초안을 저장하거나 새로고침 전 경고 제공
- 저장 실패와 손상된 JSON을 사용자에게 알리고 복구/초기화 선택지 제공

로그인을 추가할 때는 로컬 익명 데이터를 계정 데이터로 병합하는 정책과 충돌 해결 규칙도 필요하다.

## 9. 행동 분석 계획

현재 `src/domain/analytics.ts`에는 이벤트 타입이 있지만 프로덕션 전송 구현이 없다. 첫 단계에서는 개인식별정보, 제품명 원문, 증상 자유 입력을 이벤트에 보내지 않고 집계 가능한 속성만 보낸다.

### 핵심 퍼널 이벤트

- `onboarding_started`
- `consent_saved`
- `procedure_saved`
- `product_registration_started`
- `product_saved`
- `onboarding_step_viewed`
- `onboarding_resumed`
- `onboarding_completed`
- `recommendation_viewed`
- `recommendation_reason_opened`
- `recommendation_feedback_submitted`
- `check_in_completed`

### 반드시 볼 지표

- 단계별 완료율과 이탈률
- 온보딩 완료까지 걸린 시간
- 중간 이탈 후 재개율
- 제품 등록 성공률과 초안 손실률
- 추천 결과 열람률과 근거 펼침률
- 실제 사용 피드백률
- 1일/7일 재방문율

이벤트 속성은 카테고리, 온보딩 단계, 룰팩 버전, 판정 등급처럼 낮은 민감도의 집계 값으로 제한한다.

## 10. 구현 우선순위

### P0 — 신뢰 가능한 MVP

- 온보딩 완료/진행 상태 및 재개 로직
- 현재 증상과 위험 신호 입력
- 사용자 확정 알레르기/기피 성분
- 제품 버전이 구분된 전성분 데이터
- 룰 근거, 버전, 불확실성 표시
- 추천 이후 피드백
- 최소 행동 분석 퍼널
- 재방문 및 중간 이탈 E2E 테스트

### P1 — 개인화

- 안 맞았던 제품 이력과 의심 성분군
- 전체 루틴 및 제품 조합 분석
- 계절/환경/사용량 맥락
- 로그인과 기기 간 동기화
- 리뉴얼 제품 감지 및 데이터 검수 도구

### P2 — 확장

- 바코드/OCR 기반 제품 등록
- 전문가 검토 워크플로
- 근거 수준별 자동 추천 제한
- 사용자군별 성과 분석과 룰 개선 후보 생성
- 더 많은 시술, 기간, 제품군 지원

## 11. 출시 전 체크리스트

- [ ] 추천의 대상과 비대상을 명시했는가
- [ ] 위험 증상은 제품 추천보다 병원 문의를 우선하는가
- [ ] 알 수 없는 상태를 안전한 결과로 처리하는가
- [ ] 제품과 성분 데이터에 출처, 버전, 검토일이 있는가
- [ ] 리뉴얼 전후 제품이 섞이지 않는가
- [ ] 판정에 사용된 룰팩 버전을 재현할 수 있는가
- [ ] 안 맞았던 제품에서 원인 성분을 확정적으로 단정하지 않는가
- [ ] 온보딩 완료와 진행 중 상태를 구분하는가
- [ ] 같은 브라우저 재방문과 중간 이탈 복귀를 테스트했는가
- [ ] 로그인 전후 로컬 데이터 병합 정책이 있는가
- [ ] 분석 이벤트에 건강 정보나 자유 입력 원문을 보내지 않는가
- [ ] 사용자가 데이터를 내보내고 삭제할 수 있는가
